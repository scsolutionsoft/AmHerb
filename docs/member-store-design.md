# แบบระบบร้านค้าสมาชิก AM HERB

วันที่ 7 ตุลาคม 2026 — ข้อเสนอออกแบบจากโค้ดปัจจุบัน ยังไม่ได้ติดตั้งความสามารถใหม่ตามเอกสารนี้

## 1. ผลตรวจระบบเดิม

| งาน | สิ่งที่พบจากโค้ด | สิ่งที่ต้องต่อเติม |
|---|---|---|
| สมัครสมาชิก | `/Account/Register` สร้าง Identity, Member, ผู้แนะนำ และส่งอีเมลยืนยัน | ขั้นตอนเปิดร้านและสถานะความพร้อมร้าน |
| Login | `/Identity/Account/Login` ใช้อีเมล/รหัสผ่าน ยืนยันอีเมล มี lockout และทางไป 2FA | หน้าเริ่มต้นตามบทบาท และตรวจสมาชิกถูกระงับทุกคำสั่งสำคัญ |
| คลังและ POS สมาชิก | `MemberService.CreateAsync` สร้างคลังสมาชิกและ POS ประจำบัญชีให้แล้ว | ผูกหน้าร้านออนไลน์กับคลังเดียวกันอย่างชัดเจน |
| หน้าสมาชิก | `/Member` มีโปรไฟล์ เครือข่าย QR/referral, Token และคำสั่งซื้อ | ศูนย์จัดการร้านที่แยกงานซื้อของตนเองจากงานขาย |
| หน้าร้าน | `/Catalog` เป็นร้านกลาง; `/r/{code}` เก็บ referral แล้วส่งไปหน้าร้าน | หน้าร้านเฉพาะสมาชิก ชื่อร้าน URL สินค้าที่เปิดขายและเงื่อนไขจัดส่ง |
| ตะกร้า | `CartService` ใช้ cookie `am.cart`; `Cart` ไม่มี StoreId หรือเจ้าของบัญชี | ตะกร้าแยกร้าน เชื่อมบัญชีหลัง login และป้องกันการเปลี่ยนผู้ขายจาก referral |
| Checkout | ออนไลน์ใช้คลัง ID 1; POS ใช้คลังของจุดขาย | เลือกคลังจากร้านบนเซิร์ฟเวอร์ บันทึกผู้ขาย ผู้ส่ง และผู้รับเงินแยกกัน |
| สต็อก | `/Stock` กรองคลังเจ้าของ มีล็อต พร้อมขาย จอง หมดอายุ CSV | ใบตรวจนับ ปรับยอดแบบอนุมัติ สินค้ากักกัน และต้นทุนของสมาชิก |
| เบิก/โอน | `/Transfers` ขอเบิก จ่าย รับ มีสิทธิ์และหลักฐาน; หนึ่ง SKU ต่อใบ | หลาย SKU รับบางส่วน ขาด/เกิน/เสียหาย และเคลม |
| รายงานขาย | `SalesDashboardService` มีขอบเขตรายบุคคล/ภาพรวม | รายงานแยกร้าน กำไรของร้าน และกระทบยอดเงิน |
| บัญชี | `AccountingService` มีสมุดย่อยขาย/คืน; `/Accounting` ใช้ policy Payments | สมุดบัญชีร้านแยกเจ้าของ ค่าใช้จ่าย เงินรับ–จ่าย และยอดค้างชำระระหว่างบริษัทกับร้าน |

หลักฐานหลัก: `Controllers/AccountController.cs`, `Areas/Identity/Pages/Account/Login.cshtml.cs`, `Services/Foundation.cs`, `Services/StoreQueries.cs`, `Services/CommerceService.cs`, `Controllers/StockController.cs`, `Controllers/TransfersController.cs`, `Controllers/AccountingController.cs` ภายใต้ `src/AmHerb.Web` การตรวจครั้งนี้เป็นการอ่านโค้ด ไม่ใช่ผลทดสอบการใช้งานทุกเส้นทาง

## 2. รูปแบบธุรกิจที่ต้องแยกให้ชัด

ออกแบบให้รองรับสองรูปแบบ โดยเริ่มพัฒนารูปแบบที่ผู้ใช้เลือกก่อน:

| เรื่อง | สมาชิกขายและจัดส่งเอง | บริษัทจัดส่งผ่านร้านสมาชิก |
|---|---|---|
| คลังที่ใช้ | คลังของร้านที่ได้รับสิทธิ์ | คลังบริษัทที่กำหนด |
| ผู้ดำเนินการจัดส่ง | สมาชิก/พนักงานร้าน | บริษัท |
| ผู้รับเงิน | ตามการตั้งค่าที่อนุมัติของร้าน หรือบริษัทรับแทนพร้อมบัญชีพัก | บริษัท |
| ผลตอบแทนสมาชิก | ผลการขายหักต้นทุนของสมาชิก และรางวัลที่เข้าเงื่อนไข | ค่าตอบแทนตามนโยบายบริษัท |
| รายงาน | ยอดขายของร้าน ต้นทุนของร้าน ค่าใช้จ่าย | ยอดที่แนะนำ และค่าตอบแทน ไม่บันทึกเป็นเงินขายที่ร้านรับทั้งหมด |

ข้อเสนอเริ่มต้น: หนึ่งสมาชิกมีหนึ่งร้าน ร้านใช้คลังสมาชิกที่ระบบสร้างไว้ และหนึ่งคำสั่งซื้อมีหนึ่งร้าน/หนึ่งรูปแบบจัดส่ง ห้ามสลับไปใช้คลังบริษัทเมื่อของร้านหมดโดยอัตโนมัติ หากรองรับสองแบบให้แยกตะกร้าและแจ้งลูกค้าก่อนซื้อ

ต้องกำหนดก่อนพัฒนาการเงินจริง: ผู้ขายตามเอกสาร ผู้รับเงิน ผู้อนุมัติรับเงิน/คืนเงิน สิทธิ์ตั้งราคา และผู้รับภาระส่วนลด/Token ข้อเสนอนี้ไม่เปลี่ยนอัตรารางวัลเดิม และยังไม่ใช่ข้อกำหนดบัญชีหรือภาษีที่รับรองแล้ว

## 3. สมัครสมาชิกและเปิดร้าน

1. สมัครด้วยชื่อ อีเมล รหัสผ่าน และรหัสผู้แนะนำถ้ามี ใช้ Identity เดิม ไม่สร้างระบบรหัสผ่านอีกชุด
2. ยืนยันอีเมลและเข้าสู่ระบบ การสร้าง Member/role/คลัง/POS ต้องเรียกซ้ำได้โดยไม่เกิดข้อมูลซ้ำ และตรวจผลสำเร็จทุกขั้น
3. เปิดหน้าตั้งค่าร้าน: ชื่อร้าน slug โลโก้ ช่องทางติดต่อ ที่อยู่ส่งออก และเวลาทำการ
4. เลือกรูปแบบจัดส่ง คลัง รายการสินค้า และการรับเงินตามสิทธิ์ที่บริษัทอนุญาต
5. สร้างร้านสถานะ Draft; เปิดเป็น Active เมื่อข้อมูลครบและผ่านการอนุมัติที่กำหนด คลังใหม่เริ่มยอดศูนย์ ไม่มีสินค้าหรือเงินสมมติ
6. แสดงลิงก์ร้านและ QR พร้อมรายการสิ่งที่ยังต้องทำ เช่น เติมสต็อกหรือกำหนดวิธีส่ง

สถานะร้าน: Draft → PendingApproval → Active; ร้านพักขายเป็น Paused และผู้ดูแลระงับเป็น Suspended ร้านพัก/ถูกระงับไม่รับคำสั่งซื้อใหม่ แต่เอกสารเก่าและการคืนเงินยังต้องดำเนินการได้โดยผู้มีสิทธิ์

แยกสถานะ Identity, สมาชิก และร้าน การถูกระงับขายต้องไม่ทำให้ลูกค้าเสียช่องทางติดตามคำสั่งซื้อหรือขอคืนสินค้า

## 4. หน้าจอและเส้นทางที่เสนอเพิ่ม

| ผู้ใช้ | หน้า | หน้าที่ |
|---|---|---|
| ลูกค้า | `/s/{slug}` | ชื่อ/เจ้าของร้าน สินค้า ราคา สถานะพร้อมขาย ค้นหา และช่องทางติดต่อ |
| ลูกค้า | `/s/{slug}/products/{id}` | รายละเอียดสินค้า จำนวน ราคา/แพ็ก ค่าจัดส่งและวิธีรับ |
| ลูกค้า | `/s/{slug}/cart` | ตะกร้าร้านนี้ ยอดรวม ส่วนลด ค่าจัดส่ง ผู้ขายและผู้จัดส่ง |
| ลูกค้า | `/s/{slug}/checkout` | ที่อยู่ ชำระเงิน ทบทวนยอดและยืนยันคำสั่งซื้อ |
| สมาชิก | `/MyStore` | งานรอทำ ออเดอร์รอชำระ/รอส่ง ยอดขาย และแจ้งเตือนสต็อก |
| สมาชิก | `/MyStore/Settings` | ข้อมูลร้าน การเปิด–ปิด ช่องทางรับเงินและจัดส่ง |
| สมาชิก | `/MyStore/Products` | เปิดขาย/พักขายสินค้าในแค็ตตาล็อกบริษัท ราคาตามสิทธิ์ |
| สมาชิก | `/MyStore/Orders` | ค้นหา จัดสินค้า ส่งสินค้า ยกเลิก คืน และพิมพ์เอกสาร |
| สมาชิก | `/MyStore/Inventory` | คงคลัง ล็อต stock card โอน ตรวจนับ และความเสียหาย |
| สมาชิก | `/MyStore/Accounting` | เงินสด/ธนาคาร รับ–จ่าย ค่าใช้จ่าย ลูกหนี้และกระทบยอด |
| สมาชิก | `/MyStore/Reports` | ยอดขาย กำไรขั้นต้น สินค้า คลัง และสถานะเงิน |

เมนูหลักแยก “ซื้อสินค้าของฉัน” ออกจาก “จัดการร้านของฉัน” ส่วน POS, Transfers และโปรไฟล์ใช้ความสามารถเดิมต่อได้ การแสดงผลต้องรองรับมือถือ และให้เห็นชื่อร้าน/คลังที่กำลังทำงานชัดเจน

## 5. ตะกร้าและคำสั่งซื้อ

- ตะกร้าผูก StoreId + รูปแบบจัดส่ง + ผู้ซื้อหรือ guest token; คนเดียวมีหลายตะกร้าได้ แต่ checkout ทีละร้าน
- login รวมตะกร้าได้เฉพาะร้านและรูปแบบเดียวกัน แสดงรายการที่ต้องปรับเมื่อราคาหรือสต็อกเปลี่ยน
- ลิงก์ referral ของร้าน B ต้องไม่เปลี่ยนเจ้าของตะกร้าร้าน A แยก ReferrerMemberId ออกจาก StoreOwnerMemberId
- เพิ่มสินค้าไม่จองสต็อก; checkout ตรวจราคา สิทธิ์แพ็ก ร้าน คลัง ยอดพร้อมขาย และจองแบบธุรกรรม
- ราคาที่จ่ายจริง ส่วนลด ค่าขนส่ง ต้นทุน และกติการางวัลต้องมี snapshot ของรายการ ไม่คำนวณเอกสารเก่าจากราคาปัจจุบัน
- เซิร์ฟเวอร์หาผู้ขาย คลัง และบัญชีรับเงินจากร้าน ห้ามเชื่อค่าเหล่านี้จากฟอร์มหรือ URL เพียงอย่างเดียว
- payment, fulfillment และ return มีสถานะแยกกัน เพื่อรองรับจ่ายแล้วแต่ยังไม่ส่ง และคืนบางส่วน
- สถานะการส่ง: Unfulfilled → Picking → Packed → Shipped → Delivered; ก่อนส่งมีเส้นทางยกเลิกและคืนเงินตามสิทธิ์
- การชำระที่หมดอายุคืนยอดจองครั้งเดียว; หากชำระมาหลังหมดอายุต้องเข้าตรวจสอบ/จองใหม่ ห้ามยืนยันขายของที่ไม่มี
- คำสั่งซ้ำและ payment callback ซ้ำต้องไม่สร้าง order ตัดสต็อก บัญชี หรือรางวัลซ้ำ; key ต้องอยู่ในขอบเขตร้านและผู้ซื้อ
- เอกสาร guest ใช้สิทธิ์เข้าถึงที่ตรวจสอบได้; ลูกค้าร้านหนึ่งไม่เห็นข้อมูลลูกค้าร้านอื่น

## 6. คลังและต้นทุน

- ใช้ Warehouse/InventoryBatch เดิม เชื่อมกับร้าน ไม่สร้างยอดคงเหลือออนไลน์แยกจาก POS
- เลือกล็อต FEFO ภายในคลังที่อนุญาต ล็อตหมดอายุ เสียหาย และกักกันห้ามขาย
- นิยามยอด: พร้อมขาย จอง กักกัน หมดอายุ และระหว่างขนส่งไม่ทับซ้อนกัน; การย้ายตำแหน่งไม่เพิ่มจำนวนรวม
- ใบโอนใหม่มีหลายรายการและจำนวนส่ง/รับ/เสียหายแยกต่อรายการ การรับบางส่วนคงยอดระหว่างขนส่งส่วนที่ยังไม่รับ
- ใบตรวจนับมีวันที่ ผู้ตรวจนับ ยอดระบบ ยอดจริง ผลต่าง เหตุผล และผู้อนุมัติ ใช้รายการปรับยอดแทนแก้ตัวเลขโดยไม่มีหลักฐาน
- คืนสินค้าเข้ากักกันก่อนตรวจคุณภาพ แล้วจึงกลับพร้อมขายหรือบันทึกเสียหาย
- ต้นทุนซื้อของสมาชิกแยกจากต้นทุนภายในบริษัท การซื้อเติมคลังและการโอนฝากขายเป็นคนละธุรกรรม ต้องบันทึกผู้เป็นเจ้าของสินค้าด้วย
- การเติมสินค้า/โอนคลังไม่ให้รางวัลขายปลีกซ้ำ การขายปลีกจริงจึงเข้าสู่นโยบายรางวัลที่ตรวจสอบแล้ว

## 7. บัญชีร้านและการรับเงิน

ใช้สมุดย่อยแยกขอบเขตบริษัท/ร้าน พร้อม event key ป้องกันบันทึกซ้ำ เอกสารลงบัญชีแล้วแก้ด้วย reversal และเอกสารใหม่ มีผู้ทำรายการและเหตุผล

ความสามารถที่เพิ่ม: รายการรับชำระ เงินสด/ธนาคาร ค่าใช้จ่ายพร้อมหลักฐาน ลูกหนี้ลูกค้าร้าน ยอดที่ร้านต้องจ่ายบริษัท ยอดบริษัทรับแทนที่ต้องส่งคืนร้าน และการกระทบยอดตามรอบ

เครดิตบริษัทที่มีอยู่เป็นสิทธิ์สมาชิกซื้อกับบริษัท ห้ามนำไปใช้เป็นเครดิตลูกค้าร้านโดยอัตโนมัติ ต้องแยกวงเงิน ผู้อนุมัติ และขอบเขตเจ้าหนี้

สำหรับบริษัทรับเงินแทน ให้มี Settlement ระบุยอดขายที่เกี่ยวข้อง คืนเงิน ค่าธรรมเนียม ส่วนลด ผู้รับภาระ Token ยอดสุทธิ วันจ่าย และหลักฐาน ไม่ปะปนเงินพักกับรายได้ของร้านหรือบริษัท

รายงานกำไรขั้นต้นของร้าน = ยอดขายสินค้าสุทธิหลังส่วนลดและคืน − ต้นทุนขายของร้าน; รายงานหลังค่าใช้จ่ายแสดงค่าใช้จ่ายและค่าธรรมเนียมเพิ่ม พร้อมบอกฐานคำนวณ ห้ามถือ Token เป็นเงินสด หรือถือยอด referral ทั้งหมดเป็นรายได้สมาชิก

เอกสารขาย/คืนและการตั้งค่าภาษีต้องกำหนดตามผู้ขายจริงก่อนเปิดใช้งาน เอกสารนี้กำหนดโครงสร้างซอฟต์แวร์ ไม่กำหนดอัตราภาษีหรือหลักการรับรู้บัญชีแทนผู้รับผิดชอบ

| บทบาทที่เสนอ | ขอบเขต |
|---|---|
| ลูกค้า/Guest | ร้านสาธารณะ ตะกร้าและคำสั่งซื้อที่ตนมีสิทธิ์ |
| เจ้าของร้าน | ตั้งค่าร้าน ขาย คลัง บัญชีและรายงานร้านตนเอง |
| พนักงานขายร้าน | POS/คำสั่งซื้อที่ได้รับมอบหมาย ไม่เห็นต้นทุนหรือเปลี่ยนบัญชีรับเงิน |
| พนักงานคลังร้าน | จัด/ส่ง/รับ/นับสินค้าของคลังที่ได้รับมอบหมาย |
| บัญชีร้าน | ตรวจรับเงิน ค่าใช้จ่ายและรายงานเฉพาะร้านตามสิทธิ์ |
| เจ้าหน้าที่บริษัท | ทำงานข้ามร้านเฉพาะ policy ที่ได้รับ มี audit และเหตุผล |

ระยะแรกใช้เจ้าของร้านก่อน เพิ่มพนักงานผ่าน StoreUser โดยไม่ให้ role ระดับบริษัทแก่พนักงานร้าน ตรวจสิทธิ์ใน service ทั้ง read/write/export/media และงานเบื้องหลัง ห้ามใช้เพียงการซ่อนเมนู

## 9. โครงสร้างข้อมูลที่เสนอ

| ข้อมูล | ฟิลด์/ข้อกำหนดสำคัญ |
|---|---|
| MemberStore | OwnerMemberId, Slug แบบ unique, Name, Status, FulfillmentMode, DefaultWarehouseId, RowVersion |
| StoreProduct | StoreId, SkuId แบบ unique คู่, Enabled, นโยบายราคา/ช่วงมีผล |
| StoreUser / StoreWarehouse | ผู้มีสิทธิ์และคลังที่ร้านใช้ได้ ต้องตรวจเจ้าของและสถานะ |
| Cart | เพิ่ม StoreId, BuyerUserId/GuestToken, FulfillmentMode, Version, ExpiresAt |
| Order | เพิ่ม StoreId, ReferrerMemberId, Merchant/Payee/Fulfillment snapshot; เก็บ seller เดิมเพื่อความเข้ากันได้ |
| Shipment / ShipmentItem | OrderId, WarehouseId, จำนวนส่งต่อรายการ, tracking และเวลาสถานะ |
| StorePaymentAccount | ช่องทางรับเงินที่ตรวจสอบแล้ว ประวัติเปลี่ยนและผู้อนุมัติ จำกัดข้อมูลที่เปิดเผย |
| StockOwnership / MemberCost | เจ้าของสินค้า ต้นทุนสมาชิก และแหล่งเอกสาร ห้ามใช้ต้นทุนบริษัทแทนโดยไม่มีนโยบาย |
| TransferLine / TransferReceipt | หลาย SKU รับหลายครั้งและผลต่าง พร้อม key ป้องกันรับซ้ำ |
| StockCount / StockAdjustment | รายการนับ ผลต่าง หลักฐานและการอนุมัติ |
| StoreExpense / StoreReceivable | ค่าใช้จ่ายร้าน และหนี้ลูกค้าร้าน แยกจากเครดิตบริษัท |
| JournalEntry | เพิ่ม BookScope/StoreId และ unique event key ภายในขอบเขตบัญชี |
| Settlement | ผู้จ่าย/ผู้รับ รายการอ้างอิง ยอดสุทธิ และสถานะจ่าย |

ทุก FK ที่เกี่ยวกับร้านต้องตรวจความสอดคล้องของ StoreId และ owner ที่ service/ฐานข้อมูลตามที่ทำได้ พร้อมดัชนีสำหรับร้าน+สถานะ+วันที่ และ pagination รายงาน

## 10. รายงานที่ต้องมี

รายงานยอดขายรายวัน/เดือนแยกออนไลน์กับ POS, ยอดคืน/ส่วนลด, สินค้าขายดี, กำไรขั้นต้น, เงินรอตรวจ/รับแล้ว/ค้างโอนให้ร้าน, ลูกหนี้และอายุหนี้, สต็อกและ stock card, ล็อตใกล้หมดอายุ, โอนระหว่างทาง, ผลต่างตรวจนับ, ปิดกะ และค่าตอบแทน referral

ใช้วันตาม Asia/Bangkok และเวลา UTC ในฐานข้อมูล กำหนดให้ชัดว่ารายงานใช้วันที่สั่งซื้อ รับชำระ ส่ง หรือคืนสินค้า ยอดขายไม่รวมคำสั่งรอชำระ/ยกเลิกโดยไม่มีคำอธิบาย ส่งออก CSV และพิมพ์โดยใช้สิทธิ์เดียวกับหน้าจอ

## 11. แผนพัฒนาและการย้ายข้อมูล

1. วาง Store/สิทธิ์/สถานะและ migration แบบเพิ่มข้อมูล สร้างร้าน Draft ให้สมาชิกเดิม ผูกคลัง/POS เดิม ตรวจความสัมพันธ์ผิดปกติก่อนเปิดร้าน
2. เปิดหน้าร้านและตะกร้าแยกร้าน เชื่อม checkout กับคลัง ทดสอบขายพร้อมกันระหว่าง POS กับออนไลน์
3. เพิ่มจัดส่ง รับชำระ ยกเลิก คืนสินค้าและการแจ้งเตือนให้ครบวงจรสำหรับรูปแบบธุรกิจแรก
4. เพิ่มบัญชีร้าน ต้นทุนสมาชิก ค่าใช้จ่ายและการกระทบยอด พร้อมรายงานที่ตรวจเทียบเอกสารได้
5. เพิ่มคลังหลายรายการ รับบางส่วน ตรวจนับ และพนักงานร้านตามลำดับใช้งานจริง

คำสั่งซื้อและบัญชีเก่าคงความหมายเดิม ห้ามถือ SellerMemberId จาก referral ว่าเป็นร้านที่เป็นผู้ขายทั้งหมด ให้จัดเป็น Legacy/company sale และย้ายเฉพาะรายการที่มีหลักฐาน ตะกร้า cookie เดิมอยู่ร้านกลางจนกว่าผู้ซื้อเลือกย้ายอย่างชัดเจน

ใช้ feature flag เปิดร้านกลุ่มทดลองก่อน การปิด feature flag ไม่ลบเอกสารร้านที่เกิดขึ้นแล้ว สำรองข้อมูลก่อน migration และทดสอบอัปเกรดกับฐานข้อมูลสำเนา

## 12. เกณฑ์ตรวจรับ

- สมัครและเรียกซ้ำไม่สร้าง Member/คลัง/POS/ร้านซ้ำ login และอีเมลยืนยันครบเส้นทาง
- ร้าน A อ่าน แก้ ส่งออก หรือแนบหลักฐานกับข้อมูลร้าน B ไม่ได้ แม้เปลี่ยน ID ใน request
- ตะกร้า A ไม่เปลี่ยนเจ้าของจากการเปิดร้าน B หรือ login และ guest ไม่เปิดเอกสารของผู้อื่นได้
- สต็อกชิ้นสุดท้ายถูกซื้อพร้อมกันจากออนไลน์และ POS ได้สำเร็จเพียงรายการเดียว
- ยกเลิก หมดอายุ จ่ายซ้ำ ส่งซ้ำ รับโอนซ้ำ และคืนบางส่วนไม่ทำให้ยอดสินค้า/เงิน/Token ซ้ำ
- ร้านพัก/สมาชิกถูกระงับไม่สร้างคำสั่งใหม่ เอกสารเก่ายังจัดการผ่านผู้มีสิทธิ์ได้
- บัญชีแยกร้านและสมดุล รายงานเทียบได้กับเอกสารรับเงิน คืนสินค้า ต้นทุนและ settlement
- การย้ายข้อมูลไม่เปลี่ยนผู้ขาย คลัง หรือรางวัลของออเดอร์เก่าโดยอนุมานจาก referral
- ทดสอบบนมือถือและ IIS x64 พร้อมฐานข้อมูลทดสอบแยกก่อนเปิดใช้งานจริง

## 13. ประเด็นรอข้อสรุป

รูปแบบจัดส่งหลัก, ผู้รับเงิน, สิทธิ์ตั้งราคา, ความเป็นเจ้าของสต็อก (ซื้อขาด/ฝากขาย), กฎ Token ต่อร้าน, ขั้นตอนอนุมัติเปิดร้าน และความจำเป็นของพนักงานร้าน เป็นการตัดสินใจทางธุรกิจที่ยังไม่ควรฝังค่าเอง เริ่มพัฒนาโครงสร้างและหน้าร้านได้หลังเลือกขอบเขตรุ่นแรก แต่ส่วนรับเงินจริง/บัญชีต้องใช้ข้อสรุปที่ตรงกัน
