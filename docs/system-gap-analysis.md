# วิเคราะห์ระบบ AM HERB และส่วนที่เพิ่ม — 6 ตุลาคม 2026

วิเคราะห์จาก `docs/master-prompt.md`, โค้ดปัจจุบัน, การแยกคลังบริษัท/ดีลเลอร์/สมาชิก และการขาย POS ต่อผู้ใช้ ขอบเขตนี้ไม่ได้เปลี่ยนอัตรารางวัลหรือกติกาการซื้อขายเดิม

## สิ่งที่มีอยู่แล้ว

| กลุ่มงาน | ความสามารถที่พบในระบบ |
|---|---|
| สมาชิกและสิทธิ์ | Identity, roles/policies, Sponsor/closure tree, referral/QR, โปรไฟล์, wallet |
| การขาย | ร้านค้า, ตะกร้า, ราคาตามช่วงเวลา/แพ็ก, โปรโมชั่น, POS ต่อผู้ใช้, เปิด–ปิดกะ, ใบเสร็จ |
| การเงินและคืนสินค้า | ยืนยันโอนโดย Finance, รับเงินสด POS, คืนบางส่วน, คืน Token และย้อนรางวัล |
| รางวัล | เฉพาะยอดขายปลีกที่ตรวจสอบแล้ว, pending/release/expiry, ประวัติแก้ย้อนหลังไม่ได้ |
| คลัง | แยกบริษัท/ดีลเลอร์/สมาชิก, lot/FEFO, จองและตัดสต๊อก, รับคืน/ปรับยอด, แจ้งเตือน, CSV |
| รายงาน | ยอดขาย/ต้นทุน/ค่าธรรมเนียม/Token, stock report แยกสิทธิ์, audit |
| เชื่อมต่อ | CSV marketplace ทำงานได้; ผู้ให้บริการภายนอกบางส่วนเป็น adapter ที่ยังต้องเชื่อมจริง |

## ช่องว่างที่แก้ในรอบนี้

ก่อนหน้านี้ผู้ใช้มีคลังและ POS แต่ไม่มีเอกสารส่งสินค้าจากคลังบริษัทเข้าคลังส่วนตัว การรับสินค้าใหม่ทั้งสองฝั่งโดยไม่มีการโอนย้ายอาจทำให้ยอดรวมเพิ่มผิด และไม่มีหลักฐานสินค้าที่อยู่ระหว่างขนส่ง

เพิ่มโมดูล `/Transfers` ครบวงจรสำหรับใบเบิกหนึ่ง SKU ต่อเอกสาร:

1. สมาชิกขอเบิกจากคลังบริษัทเข้าคลังที่ตนเป็นเจ้าของ ผู้ดูแลคลังสร้างรายการระหว่างคลังได้
2. ใบเบิกอยู่สถานะรออนุมัติ ยังไม่จองหรือตัดสินค้า ผู้ดูแลปฏิเสธหรือผู้ขอยกเลิกได้ก่อนจ่าย
3. Warehouse/Admin/SuperAdmin อนุมัติและจ่าย โดยเลือกล็อตที่หมดอายุก่อน ไม่ใช้สินค้าหมดอายุหรือจำนวนที่จองไว้
4. ตัดจำนวนพร้อมขายต้นทางและแสดงเป็นระหว่างขนส่ง ปลายทางยังนำไปขายไม่ได้
5. เจ้าของปลายทางหรือผู้ดูแลตรวจรับครบจำนวน ระบบรับเข้าด้วยล็อต วันผลิต วันหมดอายุ และต้นทุนเดิม
6. พิมพ์ใบเบิก/ใบส่งของ ดูสถานะและเลขส่งของ รับการแจ้งเตือน และมี audit ทุกการเปลี่ยนสถานะ

กติกาความถูกต้อง:

- คงคลังทั้งเครือข่าย + ระหว่างขนส่ง ต้องไม่เพิ่มเพียงเพราะโอนสินค้า
- ส่งคำขอ/จ่าย/รับซ้ำต้องไม่เพิ่มหรือลดสต๊อกซ้ำ
- ใช้ธุรกรรมและ rowversion เพื่อป้องกันจ่ายสต๊อกเดียวกันเกินจำนวนเมื่อมีคำขอพร้อมกัน
- สมาชิกเข้าถึงเฉพาะเอกสารที่เกี่ยวข้องกับคลังตนเอง และไม่เห็นต้นทุนในเอกสาร
- การเบิกเป็นการเคลื่อนย้ายสินค้า ไม่ใช่คำสั่งซื้อ การรับชำระ หรือเหตุให้ได้รับ Token
- เมื่อส่งแล้วไม่ให้ยกเลิกย้อนยอดต้นทางโดยยังไม่ยืนยันตำแหน่งสินค้าจริง
- หากข้อมูลล็อตปลายทางขัดกับต้นทาง การรับต้องหยุดและไม่บันทึกบางส่วน

## งานลำดับถัดไปและข้อมูลที่ต้องกำหนด

| ลำดับ | ระบบ / เงื่อนไข | เหตุผลและสิ่งที่ยังต้องกำหนด |
|---|---|---|
| ก่อนเปิดใช้กับลูกค้าจริง | SMTP, บัญชีรับเงิน, SuperAdmin และข้อมูลฉลากจริง | ต้องใช้การตั้งค่าของบริษัท ไม่สร้างข้อมูลสมมติแทน |
| เมื่อเริ่มจัดส่งหลายรายการ | รับสินค้าบางส่วน/เสียหายระหว่างขนส่ง และใบเบิกหลาย SKU | เวอร์ชันนี้รับครบจำนวนต่อใบ; ต้องกำหนดผู้รับผิดชอบยอดขาด การเคลม และการอนุมัติผลต่าง |
| เมื่อเริ่มซื้อสินค้าเข้าบริษัท | ผู้จำหน่าย / ใบสั่งซื้อ / รับเข้าตาม PO | ปัจจุบันรับเข้าคลังได้ แต่ยังไม่ใช่ระบบจัดซื้อหรือเจ้าหนี้ ต้องกำหนดผู้อนุมัติและเงื่อนไขเครดิต |
| เมื่อมีการขายส่งแบบเครดิต | ลูกหนี้ดีลเลอร์ วงเงิน วันครบกำหนด และกระทบยอด | การโอนสต๊อกไม่สร้างหนี้ ต้องแยกจากการขายและตกลงนโยบายเครดิตก่อน |
| รอบตรวจนับคลัง | ใบตรวจนับและผู้อนุมัติผลต่าง | ปัจจุบันปรับยอดพร้อมเหตุผลได้ แต่ยังไม่มีเอกสารตรวจนับและล็อกช่วงนับ |
| ก่อนเชื่อมบริการจริง | PromptPay/Card, marketplace และ courier APIs | ต้องเชื่อมผู้ให้บริการจริงด้วย credentials, ทดสอบ webhook และกระทบยอด ขณะนี้ CSV/manual ใช้งานได้ |
| ก่อนใช้เป็นระบบงานหลัก | สำรอง/กู้คืนฐานข้อมูล, monitoring, การตั้งค่า IIS/HTTPS | มีแนวทาง deploy แต่ต้องกำหนดที่เก็บสำรอง รอบสำรอง ผู้รับแจ้งเตือน และทดสอบกู้คืนในสภาพแวดล้อมจริง |

รายการข้างต้นเป็นงานที่ยังไม่ได้ทำในรอบนี้ ไม่ได้อ้างว่าระบบจัดซื้อ บัญชี หรือการเชื่อม API ภายนอกเสร็จแล้ว

## วิธีทดสอบและเริ่มใช้งาน

- SQL integration tests ใช้ฐานข้อมูลทดสอบแยกจาก AmHerb ตรวจ FEFO, replay, สิทธิ์, ยกเลิก, shortage, lot conflict และ concurrent dispatch
- Browser test ใช้บัญชีสมาชิกขอเบิก ให้ผู้ดูแลจ่าย และกลับมายืนยันรับ พร้อมตรวจว่าบัญชีอื่นเปิดเอกสารไม่ได้
- เข้า `/Transfers` หลังล็อกอิน; ผู้ดูแลควรรับสต๊อกจริงเข้าคลังต้นทางก่อนจ่าย และสมาชิกตรวจจำนวนจริงก่อนรับ
- เปิด `/Stock` เพื่อดูคงคลังและระหว่างขนส่งแยกกัน การรวมใบโอนนับเอกสารครั้งเดียว แม้ต้นทางและปลายทางอยู่ในขอบเขตรายงานเดียวกัน
